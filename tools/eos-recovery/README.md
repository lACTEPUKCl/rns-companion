# Автовосстановление регистрации Squad в EOS

Пилотный обход подтверждённого на WARZONE #4 сбоя. Не исправляет источник
накопления ICMP-сокетов и не гарантирует восстановление при других причинах.

## Размещение

- Контроллер: `109.172.92.112`, `/opt/rns-eos-recovery/`, systemd timer
  `rns-eos-recovery.timer` (через 60 секунд после окончания предыдущей проверки).
- Агенты: `195.18.27.172` и `185.207.214.178`, тот же каталог.
- Конфигурация: `/etc/rns-eos-recovery/`; состояние/отчёты: `/var/lib/rns-eos-recovery/`.
- Явный список: vanila-1…4, heli, mod-1…4. Другие контейнеры недоступны агенту.
- Выделенный SSH-ключ остаётся на контроллере. На хостах: ограничение исходного IP,
  forced command, запрет forwarding/PTY; host keys закреплены отдельно.
- Исходные конфиги игры и сервис lobby не изменяются и не перезапускаются.

## Условия вмешательства

Все одновременно: пять последовательных свежих успешных опросов EOS без сервера;
выборка каталога содержит хотя бы 100 серверов; RCON отвечает; наличие игроков и очереди не блокирует восстановление; минимум две ошибки UpdateSession/EOS_NoConnection за последние 180 секунд;
минимум 1024 открытых FD; занято ≥90% диапазона 32…1023; минимум 16 неизменных
неподключённых, непривязанных IPv4 ICMP datagram-сокетов в диапазоне 32…511,
наблюдаемых не менее 120 секунд. Перед действием проверяется HTTPS-доступ к Epic.

Агент повторно проверяет PID/start ticks/boot ID, условия и inode каждого сокета.
Процесс кратко останавливается ptrace; закрываются ровно 16 выбранных FD.
Копии остаются только в процессе помощника и закрываются при выходе: новые
резервные FD в игре не накапливаются. UDP/TCP-сокеты не являются кандидатами.
Старые 16 резервных FD от ручного эксперимента #4 эта автоматизация не изменяет.

Вмешательство в FD живого процесса остаётся экспериментальным: отсутствие
привязки/пира и стабильность inode не доказывают отсутствие ссылок на FD в коде
игры. По запросу владельца от 26.09.2026 восстановление разрешено с игроками; проверки сокетов сохранены.

## Ограничения повторов и проверка результата

- Блокировка параллельных действий на контроллере и на каждом сервере.
- Состояние сохраняется до запроса изменения. Неопределённый результат SSH
  блокирует повторы; после сбоя между записью и действием приоритет у запрета повтора.
- Минимум 5 минут между попытками (окно проверки результата). Успешные восстановления не ограничивают число последующих восстановлений процесса.
- После действия до 5 минут проверяется фактическое присутствие в EOS.
- Неудача или невозможность подтвердить результат блокирует этот процесс до
  ручного разбора. Возвращение в EOS само по себе не снимает блокировку неудачи.
- Изменение boot ID/PID/start ticks начинает новую историю для нового процесса.
- Ошибка опроса/разрыв >150 секунд обнуляет серию пропусков.
- Перезапусков сервера/матча, смены карты и массовой очистки нет.

## Наблюдение и отключение

На сайте: Owner → Лобби. В строке сервера отображаются последняя попытка,
её результат и время последнего подтверждённого возвращения в EOS.
Для отсутствующего сервера есть «Очистить сокеты». Запрос owner защищён CSRF
и ставится в долговечную очередь, которую подхватывает следующий проход таймера.
Он пропускает ожидание пяти промахов, но сохраняет проверку стабильности сокетов
(120 секунд), cooldown и блокировки после ошибки. Наличие игроков не блокирует запрос.
Неисполненный ручной запрос истекает через 10 минут; если сервер сам вернулся,
запрос отменяется без очистки. История сохраняется при смене игрового процесса.

API `rns-eos-recovery-api.service` слушает только `127.0.0.1:3511` на VDS.
Сайт обращается через `rns-eos-recovery-tunnel.service` на основном игровом хосте
(`172.18.0.1:3511`). Выделенный ключ разрешает forwarding только к этому endpoint;
дополнительно требуется серверный API-ключ lobby. Браузер не получает эти ключи.

На контроллере:

```sh
systemctl status rns-eos-recovery.timer
journalctl -u rns-eos-recovery.service --since today
cat /var/lib/rns-eos-recovery/controller.json
python3 /opt/rns-eos-recovery/controller.py /etc/rns-eos-recovery/controller.json --dry-run
systemctl disable --now rns-eos-recovery.timer
```

Не прерывать выполняющееся восстановление принудительным kill; отключение
таймера предотвращает следующие запуски. Ошибки/результаты записываются в журнал
и JSON-состояние. Существующие Discord-уведомления монитора о пропаже/возврате
продолжают работать; отдельная рассылка этим сервисом не добавляется.

Для ручного снятия блокировки сначала отключить таймер, сохранить копию состояния,
разобрать причину, затем согласованно обновить состояние контроллера и хоста.
Автоматического сброса файла состояния при повреждении JSON нет.

## Проверки

Linux: `python3 -m unittest discover -p 'test_*.py' -v`.
На каждом игровом хосте: `python3 icmp_recovery.py --self-test /tmp/eos-self-test.json`.
Self-test создаёт отдельный дочерний процесс: проверяет освобождение только ICMP,
сохранение UDP/остальных FD, отсутствие резервных FD в цели и отсоединение ptrace
при отказе проверки идентичности. Рабочую игру этот тест не использует.

Не проверять восстановление искусственным повреждением регистрации живого сервера.
Полное автоматическое восстановление требует следующего естественного сбоя;
успех unit/self-tests не является доказательством такого события.
